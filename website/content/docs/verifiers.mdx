title: "Verifiers: verify Attestix credentials in any language"
description: Attestix credentials are issued once and verify offline with the Attestix verifiers. Verifiers in six languages share one conformance suite and need no Python runtime.
---

An Attestix credential is issued once, by the Python core or Attestix Cloud, and verifies **anywhere**. Verifiers in six languages check the same canonical-JSON form (Attestix's own [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)-style canonicalization, with Unicode NFC normalization) and the same Ed25519 signatures ([RFC 8032](https://www.rfc-editor.org/rfc/rfc8032)) against one shared conformance suite, [`spec/verify/v1`](https://github.com/VibeTensor/attestix/tree/main/spec/verify/v1). The Python and JS verifiers are documented as passing that suite; the Go, Rust, Java, and R ports implement it and share its vectors but are not yet documented as passing.

The proof is labelled `Ed25519Signature2020`, but because it signs Attestix's canonical JSON rather than the standard Data Integrity form, generic W3C VC verifiers will reject it. Use one of the Attestix verifiers below.

The result: a regulator, an auditor, or a peer agent can confirm a Verifiable Credential offline, with no network access and no Python runtime, and without contacting the issuer: the signature either checks out or it does not. You still have to trust that the issuer's `did:key` really belongs to the issuer, and an offline check cannot see revocation status unless it is embedded in the credential.

> **Verifier-only.** These language ports *verify* credentials and delegations; they do not *issue*. Issuance stays in the Python core (`pip install attestix`) or in Attestix Cloud. If you need to mint credentials, use Python.

## Status

Python is published to PyPI and the JS/TS verifier to npm as `attestix`. Go and Rust are publishing soon.

## Code examples

Each verifier exposes a credential-verification entry point that takes the credential JSON, resolves the issuer key from the credential's `did:key`, and returns a structured pass/fail result. No network calls.

### Python

```python
from attestix.services.credential_service import CredentialService

result = CredentialService().verify_credential_external(vc)  # the VC JSON
# -> dict with result["valid"] and per-check breakdown in result["checks"]
# Revocation is only checked if the credential is in this instance's local store.
```

### JavaScript / TypeScript

```ts
import { verifyCredential } from "attestix";

const result = verifyCredential(vc); // optional: { now, checkExpiry }
if (!result.valid) {
  console.error(result.reason, result.checks);
}
// result.valid: boolean - Ed25519 over Attestix's RFC 8785-style canonical JSON
```

### Go

```go
import attestix "github.com/VibeTensor/attestix-go"

// vc is the credential JSON as []byte
result, err := attestix.VerifyCredential(vc)
if err != nil {
    log.Fatal(err)
}
fmt.Println(result.Verify()) // signature valid AND not expired AND not revoked
```

## One signature, six readers

The shared [`spec/verify/v1`](https://github.com/VibeTensor/attestix/tree/main/spec/verify/v1) vectors define what every port must reproduce, so a conformant port gives the same verdict as Python. Python and JS are documented as passing today; the other ports are being brought to the same bar. That conformance suite, not any single implementation, is the source of truth for what "valid" means.

See the [Offline Verification Walkthrough](/docs/guides/offline-verify) for an end-to-end regulator scenario, and the [bundle wire-format spec](https://attestix.io/spec/bundle/v1) for the on-the-wire format.

> Attestix produces cryptographically signed evidence; it is an evidence-tooling system, not a legal guarantor of compliance. Blockchain anchoring, where used, targets Base L2 (Sepolia testnet by default). Always consult qualified legal counsel for compliance decisions.
