## Installation Issues

### `pip install attestix` fails with dependency conflicts

```
ERROR: Cannot install attestix because these package versions have conflicting dependencies.
```

**Solution:** Use a virtual environment to isolate dependencies:

```bash
python -m venv attestix-env
source attestix-env/bin/activate  # Linux/macOS
attestix-env\Scripts\activate     # Windows
pip install attestix
```

### Python version error

```
ERROR: Package 'attestix' requires Python >=3.10
```

**Solution:** Attestix requires Python 3.10 or later. Check your version with `python --version` and upgrade if needed.

## MCP Server Issues

### Claude Code cannot find the MCP server

```
Error: MCP server "attestix" failed to start
```

**Possible causes:**

1. **Wrong Python path** - Use the full path to the Python executable where Attestix is installed:
   ```json
   {
     "mcpServers": {
       "attestix": {
         "type": "stdio",
         "command": "/usr/bin/python3",
         "args": ["-m", "attestix.main"]
       }
     }
   }
   ```

2. **Virtual environment not activated** - If Attestix is installed in a venv, point to that Python:
   ```json
   {
     "command": "/path/to/venv/bin/python"
   }
   ```

3. **Attestix not installed in that interpreter** - Run `/path/to/python -m pip install attestix` with the same interpreter your MCP config points to. The MCP server runs over stdio only; there is no HTTP transport.

### Tools not showing up in Claude Code

**Solution:** Restart Claude Code after updating the MCP config. Run `/mcp` to verify the server is connected and showing 47 tools.

## Identity Issues

### "Identity not found" when verifying

```json
{
  "valid": false,
  "checks": { "exists": false }
}
```

**Cause:** The agent ID does not exist in `identities.json`. This can happen if:
- The identity was created with a different `ATTESTIX_DATA_DIR` (Attestix uses local JSON files, by default under `~/.attestix`)
- The identity was erased with `purge_agent_data` (GDPR Article 17). A revoked identity still exists; it fails the `not_revoked` check instead
- You're using a different Attestix instance

**Solution:** Check `identities.json` in your data directory (`~/.attestix` unless `ATTESTIX_DATA_DIR` is set). Create a new identity if needed.

### Signature verification fails

```json
{
  "valid": false,
  "checks": { "signature_valid": false }
}
```

**Cause:** The signing key has changed since the identity was created. This happens when:
- `.signing_key.json` was deleted or replaced
- You moved the Attestix data files to a different machine
- The identity was created by a different Attestix instance

**Solution:** Identities are bound to the signing key that created them. If you need to verify identities across machines, you must use the same `.signing_key.json` file (and the same `ATTESTIX_KEY_PASSWORD`, if the key is encrypted).

## Credential Issues

### "Credential has been revoked"

```json
{
  "valid": false,
  "checks": { "not_revoked": false }
}
```

**Cause:** The credential was explicitly revoked via `revoke_credential`. Revocation is permanent.

**Solution:** Issue a new credential with `issue_credential`.

### Ed25519Signature2020 verification fails externally

**Cause:** This is expected. Attestix proofs are labelled `Ed25519Signature2020` but are an Ed25519 signature over Attestix's own RFC 8785-style canonical JSON (with a base64url signature value), not the Linked Data proof procedure that standard W3C VC verifiers implement. Generic verifiers will reject them regardless of configuration.

**Solution:** Verify with the Attestix verifiers instead: the `verify_credential_external` MCP tool, `attestix credential --verify-cred <id>` for stored credentials, or the standalone verifiers (see [Verifiers](/docs/verifiers)).

## Compliance Issues

### Self-assessment blocked for high-risk system

```json
{
  "error": "Self-assessment not permitted: Annex III category not specified for high-risk system; defaulting to third-party assessment per Article 43 (fail-safe). Use assessment_type='third_party' with a notified body."
}
```

**Cause:** Under Article 43, Annex III point 1 (biometrics) needs a notified body when harmonised standards are not applied, while Annex III points 2-8 use internal control (Annex VI, self-assessment). Annex I products follow their sectoral procedures. Attestix only allows self-assessment for a high-risk profile when `annex_iii_category` is set to 2-8; if it is unset, it fails safe and requires third-party assessment.

**Solution:** If your system falls under Annex III points 2-8, create the profile with `annex_iii_category` set to that point. Otherwise record a third-party assessment:

```python
compliance_svc.record_conformity_assessment(
    agent_id=agent_id,
    assessment_type="third_party",  # not "self"
    assessor_name="TUV Rheinland AG",
    result="pass",
)
```

### Compliance status shows missing items

```json
{
  "compliant": false,
  "completion_pct": 60.0,
  "missing": ["conformity_assessment_passed", "declaration_of_conformity_issued"]
}
```

**Solution:** Follow the steps in the [EU AI Act Compliance Guide](/docs/guides/eu-ai-act-compliance). The typical workflow is:

1. Create identity
2. Record training data (Article 10)
3. Record model lineage (Article 11)
4. Create compliance profile
5. Record conformity assessment
6. Generate declaration of conformity

Note: in 0.4.1, some high-risk items (for example risk management, post-market monitoring, and incident reporting) are never marked complete by any tool, so a high-risk profile cannot currently reach `compliant: true`. Treat `completion_pct` as a checklist aid, not a legal determination.

## Blockchain Issues

### "Blockchain anchoring not configured"

```
Blockchain anchoring not configured. Set EVM_PRIVATE_KEY in .env to enable on-chain anchoring. ...
```

**Solution:** Install the blockchain extra and set the wallet key in your environment. Attestix anchors to Base Sepolia by default; set `BASE_NETWORK=mainnet` for Base mainnet. The RPC URL defaults to the network's public endpoint.

```bash
pip install "attestix[blockchain]"
export EVM_PRIVATE_KEY="your_wallet_private_key"
```

To use a provider like Alchemy instead of the public RPC:

```bash
export BASE_RPC_URL="https://base-sepolia.g.alchemy.com/v2/YOUR_KEY"
```

See the [Configuration](/docs/reference/configuration) page for all environment variables.

### Transaction fails with "insufficient funds"

**Cause:** Blockchain anchoring requires a small amount of testnet ETH on Base Sepolia for gas fees (free from public faucets).

**Solution:** Fund the wallet associated with `EVM_PRIVATE_KEY` with testnet ETH on Base Sepolia (or real ETH on Base mainnet if `BASE_NETWORK=mainnet`). Run `estimate_anchor_cost` to see `balance_eth` and `can_afford`. Public faucets include the Coinbase Base faucet and the Alchemy Sepolia faucet.

### Anchoring is optional

All core Attestix features work without blockchain. If you don't need on-chain proof, skip the blockchain configuration entirely. Identity, credentials, compliance, and provenance all work offline (resolving `did:web` or other remote DID methods still needs network access).

## Delegation Issues

### "Capability escalation denied"

```json
{
  "error": "Capability escalation denied: requested capabilities ['admin'] are not held by parent delegation"
}
```

**Cause:** When chaining delegations through the Python service (`parent_token=...`), the child delegation cannot grant capabilities that the parent delegation does not have. The `create_delegation` MCP tool does not accept a parent token, so this check does not run there.

**Solution:** Only delegate capabilities that are a subset of what the issuing agent has been granted:

```python
# Parent has: ["data_access", "reporting"]
# Child can delegate at most: ["data_access", "reporting"]
# Child CANNOT delegate: ["admin", "delete"]
```

### Delegation expired

```json
{
  "valid": false,
  "reason": "Token has expired"
}
```

**Cause:** Delegation tokens (UCAN-style, server-signed JWTs) are time-bounded. The `expiry_hours` parameter sets the lifetime.

**Solution:** Create a new delegation with `create_delegation`. Consider using longer expiry times if appropriate for your use case.

## Data and Storage

### Where does Attestix store data?

By default, Attestix creates JSON files in `~/.attestix` (override with `ATTESTIX_DATA_DIR`):
- `identities.json` - Agent identity tokens
- `credentials.json` - Verifiable credentials
- `compliance.json` - Compliance profiles, assessments, declarations
- `delegations.json` - Delegation tokens
- `provenance.json` - Training data, model lineage, and the legacy audit log
- `audit.json` - Structured, hash-chained audit events
- `anchors.json` - Local record of blockchain anchors
- `reputation.json` - Interaction records
- `.signing_key.json` - Ed25519 server keypair (keep this safe)

### How do I back up my data?

Back up the whole data directory, especially `.signing_key.json`. Without the signing key you cannot issue new artifacts under the same server DID. Existing artifacts can still be verified against the public key in the server DID, but only if you have kept that DID. You can also use `attestix export <file>` to write a portable bundle.

### How do I reset everything?

Delete the JSON data files (but NOT `.signing_key.json` unless you want a completely fresh start). Attestix will recreate empty files on next use.
