[ISO/IEC 42001:2023](https://www.iso.org/standard/81230.html) (*Information technology, Artificial intelligence, Management system*) is the first international management-system standard specifically for AI. Published in December 2023, it defines how organisations establish, implement, maintain, and continually improve an AI management system (AIMS). This page shows how Attestix's hash-chained audit records, server-signed Verifiable Credentials, and provenance records map to ISO/IEC 42001's Annex A controls and process clauses.

## Why this matters

ISO/IEC 42001 is a *management-system* standard, not a product-conformance standard. Like ISO/IEC 27001 (information security), conformance is awarded to an organisation by an accredited certification body after a defined audit programme. **Attestix does not issue ISO 42001 certifications and is not a certification body.** What Attestix ships is an evidence layer an AIMS owner can use during audit preparation, particularly for the Annex A controls that touch the AI lifecycle (data, model, deployment, monitoring), where structured, tamper-evident records can reduce manual evidence-gathering.

## The honest coverage table

The table below covers 14 representative rows spanning the Annex A control areas plus the AIMS process clauses (Clauses 4 to 10). Items marked "planned" are not in Attestix 0.4.1. Named credential types such as `ProviderAssertionCredential` are planned built-ins; today you can issue a credential of any custom type with `issue_credential`, signed by the Attestix server key.

| Control | Mitigation surface in Attestix | Coverage | Evidence shape |
|---|---|---|---|
| **Clauses 4-5** Context + Leadership: AIMS scope, AI policy, leadership commitment | None directly. You can issue a custom-type credential stating that policy and scope exist; AIMS culture is organisational. | record-only | Custom-type VC (`ProviderAssertionCredential` planned) |
| **Clauses 6-8** Planning + Support + Operation: risk treatment, documented information, operational change | Profile-based intended-purpose declaration; each state change through Attestix emits a hash-chained audit event. EU AI Act Art 9 risk-management checks are planned | partial | Audit chain (`VerifiableCheckResult` planned) |
| **A.2** Policies for AI: AI policy, alignment with other policies, review | Operator-supplied policy hash placed in a custom-type credential's claims; we do not author policy | record-only | Custom-type VC with policy hash in claims |
| **A.3** Internal organization: AI roles + responsibilities, concern reporting | Server-issued UAITs per role; `log_action` accepts only four action types (`inference`, `delegation`, `data_access`, `external_call`), so there is no dedicated concern-report entry type today | record-only | UAITs + custom-type VC + audit chain |
| **A.4** Resources for AI systems: data, tooling, compute, human | Training-data records (`record_training_data`) and model-lineage records (`record_model_lineage`), both server-signed; agent-reported actions via `log_action`. No compute or human-resource fields | partial | Signed provenance entries + `log_action` chain |
| **A.5.2-5.5** Impact assessment: process + documentation + individual + societal | FRIA template ([see FRIA page](/docs/security/fria-template)) is a document template; completeness checks are planned | record-only | Custom-type VC over the completed FRIA (`ImpactAssessmentCredential` planned) |
| **A.5.6** Environmental impact: energy + resource considerations | No dedicated fields. Operator-declared energy figures can go into a custom-type credential's claims; we record, we do not measure | record-only | Custom-type VC |
| **A.6.1.2-1.3** Responsible AI objectives + design process | Signed compliance profile with `intended_purpose` (there is no `responsible_ai_objectives` field); we record, we do not judge | record-only | Compliance profile + audit chain |
| **A.6.1.4** Requirements + specifications | No structured specifications field today (planned, cross-walked to EU AI Act Art 11 / Annex IV section 1); `record_model_lineage` captures base model, fine-tuning method, and evaluation metrics | record-only | Model-lineage entry |
| **A.6.2** Lifecycle: requirements + design + V&V + deployment + operation + technical docs + event logs | Provenance entries for data and model lineage; the `log_action` chain and the audit-event chain can serve as part of the A.6.2.8 event log (they record only what reaches Attestix); cross-walk to EU AI Act Art 12 | partial | `log_action` chain + audit chain |
| **A.7** Data: training + acquisition + quality + provenance + preparation | `record_training_data` records dataset name, source URL, license, data categories, a personal-data flag, and governance measures as free text (no acquisition date or structured quality metrics); cross-walk to EU AI Act Art 10 | partial | Signed provenance entries |
| **A.8** Information for interested parties: system documentation + external reports + incidents + transparency | A2A agent cards (unsigned); `generate_declaration_of_conformity` issues an `EUAIActComplianceCredential`. An incident-reporting collection (Art 73 cross-walk) is planned | partial | Agent card + `EUAIActComplianceCredential` (`IncidentReportCredential` planned) |
| **A.9** Use of AI systems: responsible-use process + objectives + intended use | `intended_purpose` profile + UCAN-style delegation tokens (server-signed JWTs) stating deployer-side capabilities | partial | Compliance profile + delegation tokens |
| **A.10** Third-party + customer relationships: responsibility allocation + suppliers + customers | Delegation tokens allocating capabilities across supplier/customer agents; `verify_credential_external` checks a supplier's Attestix-issued credential | partial | Delegation tokens + supplier credential |

### Tally

- **full:** 0 (no control is fully satisfied by a tool; ISO 42001 is a management-system standard; no tool *is* an AIMS)
- **strong-partial:** 0 (ratings were lowered from earlier drafts because several relied on planned credential types and fields)
- **partial:** 7 (planning/support/operation, resources, lifecycle, data, information for interested parties, use of AI systems, third-party)
- **record-only:** 7 (context/leadership, policies, internal organization, impact assessment, environment, objectives, requirements + specifications)
- **out-of-scope:** 0 (every control family has at least record-only Attestix surface)

> **Important caveat: `security_check_id` is planned for v0.5.0.** As of Attestix 0.4.1 the underlying events listed above are emitted today, but they are NOT tagged with an `iso42001.*` discriminator. Until that ships you can query the underlying records by action type and reconstruct the coverage manually.

## What we don't do

- **We do not author your AI policy.** A.2 policy controls expect the AIMS owner's documented policy. You can record a signed hash of it; we never write it.
- **We do not measure environmental impact.** A.5.6 expects the operator's energy + resource disclosure. Tools like [CodeCarbon](https://codecarbon.io/) and [ML CO2](https://mlco2.github.io/impact/) measure; you can record their output in a signed credential.
- **We do not assess substantive content of impact assessments.** In the planned v0.5 design, when a deployer asserts a FRIA section is complete + appropriate, the result will transition to `assertion_recorded`, NOT to `passed=true`. Attestix should never claim to have verified the substance of a human assertion.
- **We are not your Statement of Applicability (SoA) authoring tool.** The SoA is an AIMS-owner artefact. `attestix export` produces a portability bundle the AIMS owner can reference as evidence (a control-scoped export is planned); we do not author the SoA.
- **We do not run third-party audits.** ISO 42001 certification is awarded by accredited certification bodies (ANAB-, UKAS-, JAS-ANZ-accredited). We provide audit-ready evidence; the audit + certification are separate organisational journeys.

## How to verify our coverage yourself

### Python / CLI

```bash
# Show an agent's log_action trail and re-check its hash chain
attestix audit <agent-id>

# Show EU AI Act compliance status for an agent (JSON for CI)
attestix compliance <agent-id> --json

# Export a portability bundle as AIMS evidence
attestix export my-aims-evidence.tar.gz
```

To verify the structured audit-event chain in Python (there is no `verify-chain` CLI command):

```python
from attestix.audit import AUDIT_COLLECTION, verify_chain
from attestix.storage import default_repository

events = default_repository().list(AUDIT_COLLECTION, id_field="event_id")
print(verify_chain(events).valid)
```

### JavaScript / browser

```bash
npm install attestix
```

```javascript
import { verifyCredential } from "attestix";

const result = verifyCredential(credentialJson);
// Checks the Ed25519 signature over Attestix's RFC 8785-style canonical body
// against the issuer did:key, plus expiry. Revocation cannot be checked offline.
```

### On-chain anchor (Base L2)

There is no `anchor` CLI command. Use the `anchor_audit_batch` MCP tool or `BlockchainService().anchor_audit_batch(agent_id=...)` in Python. Anchoring requires `pip install "attestix[blockchain]"` and `EVM_PRIVATE_KEY`; it uses Base Sepolia by default and Base mainnet with `BASE_NETWORK=mainnet`. See the [Base L2 anchor walkthrough](/docs/guides/base-l2-anchor).
