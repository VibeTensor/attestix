The [NIST AI Risk Management Framework 1.0 (NIST AI 100-1)](https://www.nist.gov/itl/ai-risk-management-framework), released January 2023, is the most widely-referenced non-EU AI governance framework. Its four core functions (**GOVERN, MAP, MEASURE, MANAGE**) give organisations a vocabulary for AI risk management that is widely referenced in US federal AI governance (OMB Memo M-24-10 was rescinded and replaced by [OMB Memo M-25-21](https://www.whitehouse.gov/wp-content/uploads/2025/02/M-25-21-Accelerating-Federal-Use-of-AI-through-Innovation-Governance-and-Public-Trust.pdf) in April 2025). This page shows how Attestix's hash-chained audit records, server-signed Verifiable Credentials, and provenance records map to the AI RMF subcategories.

## Why this matters

The AI RMF is **voluntary guidance**, not a regulation. There is no "AI RMF certified" mark. NIST itself uses the language "operationalising the AI RMF", using it as a structuring framework for an organisation's own AI risk-management programme. **Attestix is evidence tooling** an organisation operationalising the AI RMF can use to gather evidence for specific subcategories, particularly those that touch the AI lifecycle, where tamper-evident audit records and signed provenance can reduce manual evidence-gathering. The AI RMF Playbook + AI 600-1 Generative AI Profile are NIST's complementary operational guides; Attestix can sit underneath both as an evidence layer.

## The honest coverage table

The table below covers 20 representative subcategories spanning the four functions (the AI RMF has 72 subcategories in total). Items marked "planned" are not in Attestix 0.4.1. Named credential types such as `ProviderAssertionCredential`, `ModelEvalCredential`, and `VerifiableCheckResult` are planned; today you can issue a credential of any custom type with `issue_credential`, signed by the Attestix server key (not by an actor or approver key).

|---|---|---|---|
| **GOVERN-1.1** Legal + regulatory requirements understood | EU AI Act compliance profile with `risk_category` and optional `annex_iii_category`. A `regulatory_jurisdiction` field is planned | record-only | Compliance profile (server-signed) |
| **GOVERN-1.4** Risk-management accountability assigned | Server-issued UAITs per role. | **GOVERN-1.5** Continuous monitoring + periodic review | No built-in scheduler. You can run `attestix compliance <agent-id> --json` on your own schedule (for example in CI); it exits non-zero when the profile is not compliant. `VerifiableCheckResult` is planned | record-only | Compliance status output + audit chain |
| **GOVERN-4.1** Safety-first culture | None. A tool does not author organisational culture | out-of-scope | n/a |
| **MAP-1.1** Intended purposes + contexts + capabilities + expectations | `intended_purpose` on the compliance profile, capabilities on the UAIT, and an A2A agent card (unsigned). A `deployment_context` field is planned | partial | Compliance profile + UAIT + agent card |

| **MEASURE-2.1** Test sets + metrics + tool documentation | Test sets can be recorded with `record_training_data` and metrics with `record_model_lineage`. `ModelEvalCredential` wrapping eval outputs is planned | partial | Signed provenance entries |
| **MEASURE-2.3** Performance + assurance criteria measured | Evaluation metrics in model lineage. Art 15 accuracy/robustness checks and `record_performance_measurement` are planned | record-only | Model-lineage entry |
| **MEASURE-2.7** Security + resilience evaluated + documented | Operator's pen-test / red-team / garak results can be recorded in a custom-type credential; cross-walk to [OWASP ASI mapping](/docs/security/owasp-agentic-top10). | **MEASURE-2.10** Privacy risk evaluated + documented | `purge_agent_data` for GDPR Art 17 erasure (it deletes rows and does not recompute the audit chain); `contains_personal_data` flag on training-data records. A `privacy_assessment` field is planned | partial | Training-data entries + audit chain |
| **MEASURE-3.2** Risk tracking for emergent risks | Operator-recorded observations via `log_action`; reputation-score drift from recorded interactions (self-reported, unsigned) | record-only | `log_action` chain + reputation record |
| **MANAGE-1.1** Go/no-go determination of contextual + societal impacts | A go/no-go decision can be recorded in a custom-type credential (server-signed). A `record_go_no_go_decision` tool is planned | record-only | Custom-type VC |
| **MANAGE-1.2** Treatment of documented AI risks | No risk-treatment ledger today; a `record_risk_treatment` ledger cross-walked to the EU AI Act Art 9 risk-management system is planned | planned | n/a today |
| **MANAGE-2.3** Mechanisms to supersede + disengage + deactivate | `revoke_identity`, `revoke_credential`, and `revoke_delegation` mark records invalid (they do not stop a running agent); delegation expiry. An Art 14(4) stop-button check is planned | partial | Revoked status + audit event |
| **MANAGE-4.1** Post-deployment monitoring | Per-agent `log_action` chain records what agents report after deployment; reputation drift. An incident-reporting collection is planned | partial | `log_action` chain + reputation record |

## What we don't do

- **We do not author your organisational culture.** GOVERN-4.1 (safety-first culture), GOVERN-2.1 (workforce diversity), and similar GOVERN subcategories are organisational and cultural. Any tool that claims to "verify culture" is overclaiming.
- **We do not run TEVV ourselves.** MEASURE-1.x and MEASURE-2.x expect your eval pipeline (Weights & Biases, MLflow, Inspect AI, garak, promptfoo). You can record their outputs in signed provenance entries or credentials.
- **We do not assess third-party risk.** MAP-3.4 + CC9.2 (SOC 2) expect Vanta / Drata / UpGuard / SecurityScorecard style vendor-risk assessment. We record relationships + signed claims.
- **We are not the AI RMF Playbook.** NIST's [AI RMF Playbook](https://airc.nist.gov/AI_RMF_Knowledge_Base/Playbook) is the authoritative subcategory-by-subcategory implementation guide. We point at evidence shapes; the Playbook tells you what to do.
- **We do not detect emergent behaviour.** MEASURE-3.2 emergent-risk tracking points at research-grade interpretability work (Anthropic interpretability, white-box probes). We record the operator's observations.
- **We do not auto-promote assertions to verifications (planned design).** In the planned v0.5 check engine, when a human asserts "yes, this met the criterion", the result will transition to `assertion_recorded`, NOT to `passed=true`.

## How to verify our coverage yourself

### Python / CLI

```bash
# Show an agent's log_action trail and re-check its hash chain
attestix audit <agent-id>

# Compliance status as JSON (exits non-zero if not compliant)
attestix compliance <agent-id> --json

# Export a portability bundle as AI RMF evidence
attestix export my-airmf-evidence.tar.gz
```

To verify the structured audit-event chain in Python (there is no `verify-chain` CLI command):

```python
from attestix.audit import AUDIT_COLLECTION, verify_chain
from attestix.storage import default_repository

events = default_repository().list(AUDIT_COLLECTION, id_field="event_id")
print(verify_chain(events).valid)
```

### JavaScript / browser

```bash
npm install attestix
```

```javascript
import { verifyCredential } from "attestix";

const result = verifyCredential(credentialJson);
// Checks the Ed25519 signature over Attestix's RFC 8785-style canonical body
// against the issuer did:key, plus expiry. Revocation cannot be checked offline.
```

### On-chain anchor (Base L2)

There is no `anchor` CLI command. Use the `anchor_audit_batch` MCP tool or `BlockchainService().anchor_audit_batch(agent_id=...)` in Python. Anchoring requires `pip install "attestix[blockchain]"` and `EVM_PRIVATE_KEY`; it uses Base Sepolia by default and Base mainnet with `BASE_NETWORK=mainnet`. See the [Base L2 anchor walkthrough](/docs/guides/base-l2-anchor).
