The [OWASP Top 10 for Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/) was published by the OWASP GenAI Security Project on 9 December 2025. It names the ten most critical security risks facing autonomous AI agents: ASI01 through ASI10. This page shows how Attestix maps each risk to a concrete evidence shape that an auditor, regulator, or insurer can inspect, and states plainly what ships today versus what is planned.

## Why this matters

Plenty of frameworks claim "10/10 coverage" of OWASP lists. Attestix's claim is narrower: **for every ASI risk, we point at a specific artefact** (a server-signed Verifiable Credential, a signed and hash-chained provenance log entry, a hash-chained audit event, or an on-chain anchor) that constitutes evidence relevant to that risk. We do not replace runtime guardrails (NeMo Guardrails, llm-guard, Guardrails AI, promptfoo). We are a **forensic record** of what agents and those guardrails reported, and credentials can be checked offline with the Attestix verifiers.

Two limits apply throughout. First, signatures are made by the Attestix server key, not by per-agent keys, so they prove "this Attestix instance recorded this", not "this agent said this". Second, structured audit events (`audit.json`) are hash-chained but not signed; only the legacy provenance log written by `log_action` is both chained and server-signed.

## The honest coverage table

"Planned" items are not in Attestix 0.4.1. Commands in the "Where to verify" column exist today.

| Risk | Mitigation surface in Attestix (0.4.1) | Coverage | Evidence shape | Where to verify |
|---|---|---|---|---|
| **ASI01:2026 Agent Goal Hijack**: "Attackers manipulate agent goals, plans, or decision paths through direct or indirect instruction injection, causing agents to pursue unintended or malicious objectives." | UCAN-style delegation tokens (server-signed JWTs) state which capabilities an agent was granted; `compliance_profile.intended_purpose` provides a comparison baseline. Attestix does not intercept actions, so an out-of-scope action is only detectable by comparing the log against the delegation afterwards | partial | Delegation token + `log_action` entries. `SecurityCheckCredential` is planned | `verify_delegation` MCP tool; `attestix audit <agent-id>` |
| **ASI02:2026 Tool Misuse & Exploitation**: "Agents misuse or abuse tools through unsafe composition, recursion, or excessive execution, causing harmful side effects despite having valid permissions." | Each committed state change made through Attestix services emits one chain-hashed audit event (`actor`, `action`, `target_id`); there are 20 such action types (for example `identity.create`, `credential.issue`, `provenance.log_action`). Read-only calls and tool calls outside Attestix are not recorded unless the agent calls `log_action` | partial | `AuditEvent` (hash-chained, unsigned); `log_action` entries (signed, chained) | `attestix audit <agent-id> --action-type external_call`; Python `attestix.audit.verify_chain` |
| **ASI03:2026 Agent Identity & Privilege Abuse**: "Delegated authority, ambiguous agent identity, or trust assumptions lead to unauthorized actions through impersonation or privilege escalation." | Server-issued UAITs (custodial: every UAIT carries the server DID, agents have no keypair of their own); UCAN-style delegation tokens with expiry and revocation; capability attenuation is enforced only when a parent token is passed through the Python service (the MCP tool cannot chain). Revocation is a status flag plus an audit event, not a signed revocation VC | partial (downgraded from "full": no per-agent keys, so the evidence cannot distinguish two agents sharing one Attestix instance, and attenuation is not available over MCP) | UAIT, delegation tokens, audit event | `attestix verify <agent-id>`; [offline verification walkthrough](/docs/guides/offline-verify) |
| **ASI04:2026 Agentic Supply Chain Compromise**: "External agents, tools, schemas, or prompts that agents dynamically trust or import become compromised, introducing malicious components." | `record_model_lineage` + `record_training_data` produce server-signed provenance entries. Agent cards are not signed. OpenSSF Model Signing (OMS) compatible signatures are planned | partial | Provenance entries (server-signed), `AgentIdentityCredential` | `get_provenance` MCP tool |
| **ASI05:2026 Unexpected Code Execution**: "Agent-generated or agent-triggered code executes without sufficient validation or isolation, enabling unauthorized system access." | `log_action` records external-call entries the agent self-reports. A sandbox-isolation declaration check is planned | record-only | `log_action` entry | `attestix audit <agent-id> --action-type external_call` |
| **ASI06:2026 Memory & Context Poisoning**: "Injection or leakage of agent memory or contextual state influences future reasoning or actions across sessions." | Attestix does not see agent memory. It can show that its own log was not altered after the fact: `verify_chain` detects post-hoc tampering with audit events and returns a `VerifyChainResult` pointing at the first broken event | record-only | Hash-chained audit events and `log_action` entries | Python `attestix.audit.verify_chain`; `attestix import <bundle> --verify-only` |
| **ASI07:2026 Insecure Inter-Agent Communication**: "Messages exchanged between agents, planners, and executors become manipulated through interception, injection, or spoofing." | No message-level signing ships today. You can issue a credential with a custom type over a message digest (`issue_credential`), but it is signed by the server key, not the sending agent. An `InteractionCredential` is planned | record-only | Custom-type VC (server-signed); optional Base L2 anchor | `attestix credential --verify-cred <credential-id>`; `verifyCredential()` in the `attestix` npm package |
| **ASI08:2026 Cascading Agent Failures**: "Small agent failures propagate through connected systems, causing large-scale impact via tool chains or resource exhaustion." | Per-agent `log_action` chains support post-mortem reconstruction. Cross-agent causal links (`causal_parent_event_id`) and an incident-reporting collection are planned | record-only | Per-agent `log_action` chain; `IncidentReportCredential` is planned | `attestix export <bundle-file>` for offline reconstruction |
| **ASI09:2026 Human-Agent Trust Exploitation**: "Human over-reliance on agents is exploited through misleading explanations, authority misrepresentation, or false certainty." | Today: `log_action` records `decision_rationale` and `human_override`, and compliance profiles record `human_oversight_measures` as free text. Article 14 checks and a `ProviderAssertionCredential` that separates system-verified from provider-asserted results are planned | record-only | `log_action` entries, compliance profile | `attestix audit <agent-id>`; `attestix compliance <agent-id>` |
| **ASI10:2026 Rogue Agents**: "Agents act beyond intended objectives due to goal drift, collusion, reward hacking, or exceeding designed autonomy boundaries." | `revoke_identity`, `revoke_credential`, and `revoke_delegation` act as an operator kill-switch in the Attestix record (they do not stop a running agent); delegation expiry bounds how long a grant is valid; reputation scores can show downward drift | partial | Revoked status + audit event, expired delegation token, reputation record | `attestix credential --revoke <credential-id>`; `attestix verify <agent-id>` |

**OWASP source for every quoted description above:** [OWASP Top 10 for Agentic Applications 2026](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/).

### Tally

- **full:** 0
- **partial:** 5 (ASI01, ASI02, ASI03, ASI04, ASI10)
- **record-only:** 5 (ASI05, ASI06, ASI07, ASI08, ASI09)
- **out-of-scope:** 0

We do not claim "10/10 mitigated". We claim **10/10 mapped to a concrete evidence shape**, most of it record-keeping. The difference matters: see [What we don't do](#what-we-dont-do) below.

> **Important caveat: `security_check_id` is planned for v0.5.0.** As of Attestix 0.4.1 the underlying events listed above are emitted today, but they are NOT tagged with a namespaced `security_check_id` discriminator, and `SecurityCheckCredential` and a CLI filter by security check do not exist yet. Until then you can query the underlying events by action type and reconstruct the coverage manually.

## What we don't do

The following are intentional non-goals. The most honest section of any security framework is the gap statement.

- **No runtime prompt-injection detection.** ASI01 (Goal Hijack) is addressed only *after the fact*, by comparing the log against delegation scope; we do not analyse prompts in real time. Pair Attestix with [NeMo Guardrails](https://github.com/NVIDIA/NeMo-Guardrails), [Guardrails AI](https://www.guardrailsai.com/), [llm-guard](https://github.com/protectai/llm-guard), or [promptfoo](https://www.promptfoo.dev/) for the runtime layer and record their decisions in Attestix.
- **No code sandbox.** ASI05 (Code Execution) is `record-only` because executing code safely is the host runtime's job (Docker, gVisor, Firecracker, language-level sandboxes). We record what the agent reports it executed, and when, but we do not block the call.
- **No real-time cascade detection.** ASI08 (Cascading Failures) is observability (Datadog, Honeycomb, OpenTelemetry traces). Operators detect cascades via their existing monitoring; Attestix's export bundle helps reconstruct *which* agent recorded *what* in *what order*.
- **No hallucination detector.** We do not score the truthfulness of LLM output. We record what the agent reported; downstream review can compare it against the declared `intended_purpose`.
- **No per-agent keys.** Every signature is made by the Attestix server key. Evidence shows what the Attestix instance recorded, not independent proof from each agent.
- **No assertion-to-verification promotion (planned design).** In the planned v0.5 design, when a human asserts "yes, the residual risk is acceptable", the result will transition to an `assertion_recorded` state, NOT to `passed=true`. Attestix should never claim to have verified the substance of a human assertion.

## How to verify our coverage yourself

### Python / CLI

```bash
# Show an agent's log_action trail and re-check its hash chain
attestix audit <agent-id> --action-type external_call

# Verify an agent's UAIT (existence, revocation, expiry, signature)
attestix verify <agent-id> --json

# Export a portability bundle (audit events and anchors included by default)
attestix export my-agent-bundle.tar.gz

# Check a bundle's manifest, per-table hashes, and audit chain without importing
attestix import my-agent-bundle.tar.gz --verify-only
```

To verify the structured audit-event chain directly in Python:

```python
from attestix.audit import AUDIT_COLLECTION, verify_chain
from attestix.storage import default_repository

events = default_repository().list(AUDIT_COLLECTION, id_field="event_id")
result = verify_chain(events)
print(result.valid, result.broken_event_id, result.failure_reason)
```

### JavaScript / browser

```bash
npm install attestix
```

```javascript
import { verifyCredential } from "attestix";

const result = verifyCredential(credentialJson);
// Checks the Ed25519 signature over Attestix's RFC 8785-style canonical body
// against the issuer did:key, plus expiry. No network calls. Revocation cannot
// be checked offline.
```

The npm package is [Apache-2.0 licensed](https://www.npmjs.com/package/attestix), requires Node 18+, and depends only on `@noble/curves`. A reviewer with no Python install can verify an Attestix-issued credential with it.

### On-chain anchor (Base L2)

Tamper-evidence for the evidence itself. Anchoring uses Base Sepolia by default and Base mainnet with `BASE_NETWORK=mainnet`; it requires `pip install "attestix[blockchain]"` and `EVM_PRIVATE_KEY`. See the [Base L2 anchor walkthrough](/docs/guides/base-l2-anchor).

There is no `anchor` CLI command. Use the `anchor_audit_batch` MCP tool, or the Python service:

```python
from attestix.services.blockchain_service import BlockchainService

result = BlockchainService().anchor_audit_batch(agent_id="attestix:...")
```

Note that `anchor_audit_batch` anchors the agent's `log_action` entries (the legacy provenance log), not the structured audit events.
