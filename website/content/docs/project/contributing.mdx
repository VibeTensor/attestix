Thank you for your interest in contributing to Attestix. This guide covers how to get started, the development workflow, and project conventions.

## Getting Started

### Prerequisites

- Python 3.10+
- Git

### Setup

```bash
git clone https://github.com/VibeTensor/attestix.git
cd attestix
python -m venv .venv
source .venv/bin/activate  # On Windows: .venv\Scripts\activate
pip install -e ".[dev]"
```

### Verify Setup

```bash
python -m attestix.main
# Should print "Attestix MCP server loaded: 47 tools registered" to stderr
# Then wait for MCP client connections on stdio
```

Press Ctrl+C to stop.

## Project Structure

The installable package lives in `attestix/`; tests, docs, and examples are at the repository root. Top-level `.py` files and directories outside `attestix/` (such as the root `main.py`) are deprecated back-compat shims.

```
attestix/                 # repository root
  attestix/               # the package
    api/                  # REST API (FastAPI, [api] extra)
    audit/                # Structured, hash-chained audit events + verify_chain
    auth/                 # Cryptography (crypto.py), post-quantum (pqc.py), token parsing, SSRF guard
    blockchain/           # EAS / Merkle helpers
    idempotency/          # Idempotency-key store and middleware
    integrations/         # LangChain, OpenAI Agents SDK, CrewAI
    portability/          # Bundle export / import
    services/             # Business logic (one service per module)
    signing/              # Pluggable Signer seam (in-process Ed25519 default)
    storage/              # Pluggable Repository seam (file, memory)
    tenancy/              # Tenant context
    tools/                # MCP tool definitions (thin wrappers around services)
    cli.py                # `attestix` command-line interface
    config.py             # Data directory, storage paths, load_*/save_* helpers
    errors.py             # Error handling and logging
    main.py               # MCP server entry point (python -m attestix.main)
  tests/                  # unit, e2e, integration, benchmarks, ...
  docs/                   # Documentation
  examples/               # Runnable example scripts
```

### Architecture Rules

1. **Services contain all logic.** Tool files are thin wrappers that call service methods.
2. **Services never import from tools.** Dependencies flow: tools -> services -> config/auth.
3. **All output to stderr.** `builtins.print` is redirected to stderr to protect MCP JSON-RPC on stdout.
4. **Storage goes through the Repository seam.** Use the `load_*` / `save_*` helpers in `config.py` (thin shims over the default file `Repository`, with file locking and atomic writes) or `attestix.storage`, not direct file I/O.
5. **Signing and audit.** Sign persistent records through the `Signer` seam (UAITs, VCs, compliance and provenance records are server-signed), and emit one structured audit event per committed state change via `safe_emit`. Audit events are hash-chained, not signed.

## How to Contribute

### Reporting Issues

Open an issue on GitHub with:
- What you expected
- What happened
- Steps to reproduce
- Python version and OS

### Submitting Changes

1. Fork the repository
2. Create a feature branch: `git checkout -b feature/your-feature`
3. Make your changes
4. Run the test suite to verify nothing is broken:
   ```bash
   # Run the full suite (unit, e2e, integration, conformance benchmarks)
   pytest tests/ -v -m "not live_blockchain"

   # Or run in Docker for a clean environment
   docker build -f Dockerfile.test -t attestix-bench . && docker run --rm attestix-bench
   ```
5. Commit with a descriptive message
6. Push to your fork and open a Pull Request

### Pull Request Guidelines

- One feature or fix per PR
- Keep changes focused - avoid mixing refactoring with new features
- Update documentation if you change tool parameters or behavior
- Add an example script if you add a new module

## Code Conventions

### Style

- `ruff check` runs in CI and must pass; `ruff format --check` also runs but is advisory
- Use type hints for function signatures
- Docstrings on all public methods and classes
- Keep imports sorted: stdlib, third-party, local

### Naming

- Services: `{module}_service.py` with a class named `{Module}Service`
- Tools: `{module}_tools.py` with a `register(mcp)` function
- Storage files: lowercase `{module}.json`
- IDs: prefixed with module abbreviation (e.g., `attestix:`, `comp:`, `assess:`, `urn:uuid:`)

### Error Handling

Most service methods return error dicts instead of raising. Expected failures return `{"error": "..."}` directly; unexpected exceptions go through `log_and_format_error`, which logs the details and returns a sanitized message (exception type only, no paths or internals):

```python
from attestix.errors import ErrorCategory, log_and_format_error

def my_method(self, agent_id: str) -> dict:
    try:
        agent = self._find_agent(agent_id)
        if not agent:
            return {"error": f"Agent {agent_id} not found"}
        # ... do work
        return {"result": "success"}
    except Exception as e:
        msg = log_and_format_error(
            "my_method", e, ErrorCategory.IDENTITY, agent_id=agent_id,
        )
        return {"error": msg}
```

### Adding a New Module

1. Create `attestix/services/your_service.py` with a service class
2. Create `attestix/tools/your_tools.py` with a `register(mcp)` function
3. Add storage helpers to `attestix/config.py` if needed
4. Add an error category to `attestix/errors.py` if needed
5. Import and register in `attestix/main.py`
6. Update the tool count in the `attestix/main.py` docstring and startup message
7. Add documentation to `docs/api-reference.md` and the website API reference
8. Create an example in `examples/`

## Security

- Never return private keys in tool responses
- Exclude mutable fields (proof, credentialStatus) from signature payloads
- Use `secrets` module for generating random identifiers
- Validate all URLs before making HTTP requests (SSRF protection)
- Report security vulnerabilities privately via email, not public issues
